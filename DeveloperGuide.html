Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

Each of the four main components (also shown in the diagram above),

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

CommandBox owns a session-scoped CommandHistory. It records ordinary command submissions and uses it to replace the command box text when the user presses the Up or Down arrow key.

MainWindow installs a scene-level key-event filter for Tab navigation. It treats the command box, result display, patient list, and patient-details ScrollPane as four focus sections, routing both Tab directions explicitly so that the empty details panel remains reachable and descendants such as details labels or scrollbar controls do not become additional stops. The currently focused section receives a light-gray, 2-pixel outline; every section reserves the same border space even when unfocused. The menu bar is not part of this cycle. The details panel handles its six scrolling keys locally, so command-history and patient-list arrow-key behavior remains scoped to those controls. The patient list scrolls only as needed to keep the selected patient card fully visible.

MainWindow manages a separate HelpWindow for offline command discovery and access to the full User Guide. See Help window for its layout, lifecycle, and external-action boundaries.

Logic component

API : Logic.java

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which dispatches it to the parser for that command. Parser instances may be reused or created on demand depending on their state and dependencies.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. A command that needs more input returns a CommandResult containing a CommandInputRequest. LogicManager stores at most one pending request and sends the next command-line input directly to it without parsing that input as a command.
  4. The command can communicate with the Model when it is executed or when requested input is handled (e.g. to delete a person after confirmation).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  5. The result of command execution or input handling is encapsulated as a CommandResult object which is returned from Logic. The result also tells LogicManager whether it should save the patient data.

How the parsing works:

  • When called upon to parse a user command, AddressBookParser creates or reuses the appropriate XYZCommandParser (XYZ is a placeholder for the command name, e.g., AddCommandParser). That parser creates an XYZCommand object (e.g., AddCommand), which AddressBookParser returns as a Command.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

AddressBookParser creates and retains one NextCommandParser when it is constructed, supplying a configurable Clock. Each next command uses that parser and receives the same clock. Other parsers, such as PrevCommandParser, are created on demand for each command. Reusing the next-command parser retains the clock dependency, not a startup timestamp: eligibility checks read the clock during command execution.

Model component

API : Model.java

The Model component,

  • stores Doc's patient records i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both patient data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

When the patient data file does not exist, MainApp initializes the model with the seven records returned by SampleDataUtil#getSampleAddressBook. The sample patients are George Miller, Priya Nair, Aisha Rahman, Marcus Lim, Mei Lin Tan, Daniel Wong, and Noor Aziz. If an existing data file can be loaded successfully, including one with no records, its contents take precedence over these samples. If an existing data file cannot be loaded—for example, because it is malformed or contains conflicting records—MainApp starts with an empty address book.

Because almost every command saves the address book, the next command would overwrite the unreadable file. MainApp#loadInitialData therefore first calls Storage#backupAddressBook, which copies the file to a sibling named addressbook-invalid-<yyyyMMdd-HHmmss>.json without overwriting any existing backup. It returns the empty address book together with a warning that gives the first line of the load error and the backup's location, or, if the backup fails, tells the user to copy the file before entering any command. MainApp#start passes the warning to Ui#showStartupWarning, which shows it in a dialog once the main window is open.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Help window

Help is an offline command directory with short descriptions and syntax templates for all supported commands, with access to the full User Guide for validation rules and examples. See Viewing help for user instructions.

MainWindow retains one HelpWindow and reuses it for command, F1, and menu requests. The window is non-modal, so the main window remains usable. Closing Help returns focus to CommandBox, which restores the saved caret and selection. F1 and the menu call the UI directly; unlike typed help, they do not answer a pending input request.

Layout and content

HelpWindow.fxml places the command groups in one column inside a ScrollPane, in the centre of a BorderPane. The groups are Manage patients and visits (add, edit, next, prev, delete, clear), Find and view patients (list, find, view, sort, agenda), and Application controls (help, exit). Each command entry contains its description, a syntax template, and any optional-field continuation row. The default window may require vertical scrolling as the templates make the directory longer. A fixed footer holds the URL, buttons, and feedback so these controls remain accessible while the command list scrolls. HelpWindow.css supplies the presentation styles.

The complete user-facing syntax reference is maintained in the User Guide command summary. This section focuses on the Help window's implementation boundary instead of duplicating every command template. The edit and find descriptions state that at least one field is required. The legend is UPPERCASE: replace with your values · [ ]: optional · ...: repeatable. INDEX uses the displayed patient list number; date and emergency-contact meanings follow the detailed User Guide.

HelpWindow.show() focuses the command list, which is a Tab stop so users can return from the guide buttons. A muted keyboard hint and the notation legend UPPERCASE: replace with your values · [ ]: optional · ...: repeatable introduce scrolling and the syntax placeholders. They belong to the scrolling content, not the fixed footer, to preserve command space in small windows.

Static labels keep the directory independent of parser implementation; the FXML entries must still be maintained when command syntax changes. When AddressBookParser gains, loses, or renames a command, or when a command's syntax changes, update its FXML entry, the expected inventory and templates in HelpWindowTest, and the command summary in the User Guide. That test is the executable inventory check: it verifies command order, descriptions, templates, notation, focus, wrapping, scrolling, final-command access, and minimum-size footer space with feedback shown.

External guide actions

MainApp passes HostServices.showDocument through UiManager and MainWindow as a browser-opening action. HelpWindow also accepts a replaceable clipboard action, so tests can simulate failures without opening a browser or changing the system clipboard. For example, when copying is rejected, Copy URL shows failure feedback but Open User Guide remains available.

Browser feedback confirms only a launch request, not page loading; no network preflight is performed. Clipboard success requires Clipboard.setContent to return true. Detectable failures are logged and shown without hiding the URL or disabling the controls. HelpWindowActionsTest checks failure feedback, fallback actions, and retries. The manual checks cover native window behaviour and real browser/clipboard integration.

Optional emergency contacts

Person stores an immutable EmergencyContact value. Its empty string represents an absent contact, so existing constructors and records remain compatible. Nonempty values contain a phone number, optionally preceded by a name and comma, validated using the existing Name and Phone rules. Contact details do not affect identity.

AddCommandParser and EditCommandParser recognize ec/[NAME, ]PHONE_NUMBER and reject incomplete, invalid, or repeated contact fields before execution. add rejects an empty ec/; edit uses it to clear the contact. EditPersonDescriptor distinguishes an omitted contact from a replacement or an explicitly empty contact. EditCommand and NextCommand preserve contacts when updating unrelated fields. Patients can retain both an emergency contact and previous visit dates. Contact-only edits preserve the visit record, and scheduling the next visit appends the current datetime without clearing the contact.

JsonAdaptedPerson saves PHONE_NUMBER or the canonical NAME, PHONE_NUMBER string. Missing or null contact fields from older records map to an absent contact. Invalid nonempty stored contacts cause a data-loading error. PatientDetailsPanel shows Emergency Contact: PHONE_NUMBER (NAME) immediately below the patient's phone number, omits the parentheses when the name is absent, and hides the row for absent contacts.

Representation and validation

The model uses an empty EmergencyContact value rather than a null field. This preserves the non-null invariant of Person and allows callers of the existing constructor to create patients without contacts. ParserUtil#parseEmergencyContact rejects blank input for additions and validates nonempty replacement contacts. For edits, EditCommandParser maps an explicitly empty or whitespace-only ec/ to EmergencyContact(""). An omitted prefix leaves the descriptor field null, preserving the existing contact. An empty contact object counts as a supplied field and clears the saved value, even when no contact was previously recorded.

Validation accepts a phone number alone or exactly two comma-separated details. A supplied name must satisfy Name#isValidName, and the required phone must satisfy Phone#isValidPhone. Blank names beside a comma are rejected; omit both the name and comma for a phone-only contact. The constructor trims whitespace and stores PHONE_NUMBER or NAME, PHONE_NUMBER. EmergencyContact#toDisplayString produces PHONE_NUMBER or PHONE_NUMBER (NAME) for the UI. Person#equals and Person#hashCode include the contact; Person#isSamePerson continues to use only the patient's normalized name and phone. Sharing an emergency contact does not make two patients duplicates.

Automated verification

  • EmergencyContactTest covers valid, absent, malformed, and null values, formatting, equality, and patient identity.
  • EmergencyContactIntegrationTest exercises parsing, execution, viewing, and storage through LogicManager. It checks adding, replacing, and clearing contacts, field order, whitespace, duplicate prefixes, invalid indices, filtered-list selection, and preservation during unrelated commands. Rejected inputs must leave both the model and saved file unchanged.
  • JsonAdaptedPersonTest checks missing contact fields and invalid stored contact details.
  • NextCommandTest includes a patient with a contact to check preservation when scheduling the next visit.
  • PatientDetailsPanelTest checks the exact display text, its position immediately after the phone label, wrapping, and hiding the row when switching to a patient without a contact.

Testing a newly built JAR

Use JDK 25 and run ./gradlew shadowJar from the repository root (.\gradlew.bat shadowJar on Windows). Close any previously running instance before launching build/libs/doc.jar. Building or replacing the JAR does not reload classes in an existing application process. An edit usage message without [ec/[NAME, ]PHONE_NUMBER] indicates that the running build does not include optional contact-name support. Use a separate folder with disposable data for manual testing; the application uses paths relative to its working directory for patient data and preferences.

Visit record model

A visit record contains the patient's current datetime and the previous datetimes retained by next. The current datetime is always required, even when no further visit is planned. Retained datetimes do not verify attendance or completion, and notes remain patient-level. See the User Guide for the user-facing distinction between advancing and rescheduling.

Each immutable Person has one required current VisitDate and a non-null List<VisitDate> named previousVisitDates. The previous dates are strictly increasing, oldest first, and each must be strictly earlier than the current date. Comparisons use parsed LocalDateTime values, including the time: leading-zero variants of the same datetime are equal, while different times on one day are allowed. These invariants do not depend on the clock, so the passage of time does not invalidate a record.

The constructor takes an immutable defensive copy and rejects null entries or invalid chronology rather than sorting or repairing the input. The constructor without previous dates creates an empty list. Equality and hashing include previous dates; patient identity still uses the normalized name and phone number.

Editing a patient or copying it with PersonBuilder preserves previous dates. The command-specific transitions are described under Scheduling the next visit and Restoring the previous visit.

JsonAdaptedPerson writes previousVisitDates as an ordered array of visit-date strings. Missing or JSON-null arrays load as empty lists for compatibility with older files; visitDate is still required. Non-arrays, null or malformed entries, invalid chronology, and duplicates within a record follow the existing invalid-data path. No entries are sorted, deduplicated, or dropped to repair an invalid file.

Displaying visit records

PatientDetailsPanel shows Previous visit dates: below the current visit and above the note, with one datetime per line or No previous visit dates for an empty record. It reverses the dates only for display, placing recent visits first while preserving oldest-first storage. The existing ScrollPane accommodates long records without imposing a limit on the number of retained dates.

The details ScrollPane resets its vertical value immediately when a record is rendered and once more after JavaFX lays out the updated content. This handles records of different lengths and repeated views of the same patient. Each main-window section reserves a fixed-width border whose color changes only for the focused section, keeping the panel geometry stable while making the focus stop visible.

The current datetime includes a calendar-day label in parentheses: Past, Today, or Upcoming. PatientDetailsPanel uses an injected Clock (the system's local clock in production) and reads its current LocalDate once per setPerson call. It compares calendar dates, so both earlier and later times today receive Today. This display-only label does not affect stored data, next eligibility, or the sort cutoff. Re-rendering details recomputes it; there is no automatic midnight refresh. Fixed-clock tests cover day and time-zone boundaries without changing the system clock. See Calendar labels for current visits for manual checks.

Visit-record roadmap: Person owns the current and immutable previous-date state; NextCommand appends the old current datetime before replacing it; PrevCommand pops the latest previous datetime and discards the old current one; LogicManager saves successful mutations and the UI renders the resulting record. The sections below follow this same model → command → persistence and display path.

Duplicate patient identity, visit dates, and name confirmation

Doc normalizes names only for duplicate detection. Normalization trims surrounding whitespace, replaces each sequence of spaces with one space, and converts letters to lowercase using Locale.ROOT. The accepted Name#fullName value is retained for display and storage, and Name#equals remains an exact value comparison.

Doc distinguishes a true duplicate from a name duplicate:

  • A true duplicate has the same normalized name and exact phone number as an existing patient. Person#isSamePerson implements this identity rule. UniquePersonList rejects true duplicates, so the same invariant applies to commands, model replacement, and data loaded from JSON. A true duplicate is rejected without offering confirmation.
  • A name duplicate has the same normalized name but a different phone number. Person#hasSameName identifies this weaker match. UniquePersonList permits name duplicates, but add and an edit that changes a patient's name require confirmation before creating one.

Patients with different names but the same phone number are neither true duplicates nor name duplicates, so they are accepted without confirmation. This preserves phone numbers shared by a household or clinic while using name and phone together to identify a patient record.

Model#hasPerson exposes the true-duplicate check, while Model#hasPersonWithSameName exposes the weaker warning check. Person#isSamePerson compares phones with Phone#isSameNumber, which ignores everything except digits, so a number re-entered with spaces or dashes is still recognized as the same patient. Phone#equals stays an exact comparison, so changing only a number's formatting is still a real edit.

Visit dates and times form a separate invariant across all current and previous dates. Person#hasCommonVisitDate compares the complete records using parsed VisitDate equality. UniquePersonList#containsSameVisitDate checks the full stored collection, including patients hidden by a filter. add, setPerson, and setPersons throw DuplicateVisitDateException rather than allowing two records to use the same value. This covers command mutations, model replacement, sample data, and direct model use. JsonSerializableAddressBook performs the same check while loading and reports an invalid data file with a visit-date-specific message.

Model#hasPersonWithSameVisitDate exposes the scheduling check. How add applies these rules, and when it asks for confirmation, is described in Adding a patient: validation and confirmation.

EditCommand captures the selected patient without changing the displayed list. It similarly rejects a true duplicate or a datetime shared with another patient's current or previous dates before requesting confirmation, previewing the matching identity or visit-date record. Replacement checks compare the complete candidate while excluding the original target. This permits unchanged dates and moving a patient's own dates between current and previous fields. The command asks for confirmation only when the requested edit changes the name to one already in use; editing other fields of a patient whose name is already shared does not prompt again. It reports the number of matching names, previews the first match, captures the original and edited Person objects, then verifies on confirmation that the original record still exists and that the edit still creates neither a true duplicate nor a visit-date conflict.

CommandResult carries the preview together with a name-duplicate confirmation request. CommandException carries the preview for banned identity and visit-date conflicts. MainWindow sends either preview to PatientDetailsPanel, using the same presentation as view, while feedback remains in ResultDisplay. A successful add restores the full patient list, while a successful edit preserves the active filter and sort comparator. A rejected or cancelled operation leaves the displayed list unchanged. While a confirmation is pending, the command box treats the next submission as the confirmation response, so displayed indices cannot be used by another command until the doctor confirms or cancels.

Adding a patient: validation and confirmation

add checks a new patient in three stages. Errors stop the command, while warnings only ask the doctor to confirm.

  1. Parsing. AddCommandParser requires n/, p/, a/, and vd/, rejects text before the first prefix and repeated single-valued prefixes, and validates each field through ParserUtil. Any ParseException is wrapped so that every failure starts with The patient is not added due to:.
  2. Rejection rules. AddCommand#execute calls validateNoConflicts, which uses DuplicatePersonFinder to look for a true duplicate (same normalized name and phone) and then for a stored patient using the same current or previous visit time. Either case throws a CommandException that carries the matching patient, so MainWindow shows that patient in the details panel. These rules are never overridable.
  3. Warnings. collectWarnings gathers every warning that applies: a name duplicate, and a visit day that already has Model.MAX_VISITS_PER_DAY (7) or more current visits. With no warnings, the patient is added immediately. Otherwise, the warnings are joined into one prompt ending with Add NAME anyway?, so the doctor confirms once even when both apply. When there is a name duplicate, the result also previews the first matching patient.

The prompt is a CommandInputRequest created with CommandInputRequest#createConfirmation, whose confirmed action is AddCommand#addPerson. The sequence diagram below shows a name duplicate on a full day. The first execute returns a result that holds the request and does not save. LogicManager keeps the request pending, so the doctor's next input, y, goes to the request instead of the command parser.

addPerson calls validateNoConflicts again before Model#addPerson. The proposed Person was captured before the prompt, so this recheck stops a duplicate or a visit-time conflict that appeared while the prompt was open from being saved. Only the confirmed result asks LogicManager to save, so a cancelled addition never writes the data file.

Aspect: how several warnings are confirmed

  • Alternative 1 (current choice): Collect every warning and ask once.
    • Pros: One y per addition. The doctor sees every concern together before deciding.
    • Cons: A longer prompt when both warnings apply.
  • Alternative 2: Ask about each warning in turn, chaining one confirmation request per warning.
    • Pros: Each prompt is short and focused.
    • Cons: A second y is easy to give without reading it, and the first y can look like it already added the patient.

Duplicate-detection limitations

Duplicate detection is a heuristic because Doc does not assign a permanent patient identifier:

  • Two different patients with the same normalized name and phone number cannot both be stored, such as family members who share a name and contact number. A distinguishing name component or different contact number is required.
  • A returning patient with both a changed name and changed phone number is not detected as a possible duplicate.
  • Normalization does not understand nicknames, reordered names, misspellings, transliterations, or equivalent accented forms. It performs no fuzzy or culture-specific matching.
  • Phone numbers are compared by their digits only. Equivalent numbers entered with and without a country code are not detected as the same number.
  • Collapsing whitespace and ignoring case can warn about two distinct names whose intentional difference is only capitalization or spacing.

A future patient-ID feature should replace name and phone as identity fields if Doc needs to distinguish these cases without relying on user confirmation or spelling conventions.

Current implementation limitations

The current implementation does not provide an in-app migration or recovery workflow for data that conflicts with the new duplicate rules:

  • A file accepted by an older version can become invalid when two records have the same phone number and names that differ only in letter case or repeated spacing. The normalized names now make those records true duplicates.
  • A file accepted by an older version can also become invalid when two records use the same visit date and time.
  • For either conflict, Doc reports the loading problem and starts with an empty patient list. The conflicting file is not backed up automatically, and a command that triggers saving, such as list, can replace it with the empty patient list. Users must back up the file and resolve the conflicts manually before migration.

Visit-time conflict limitations

The visit-date rule prevents only exact scheduling collisions:

  • Equality is checked to the minute using the parsed LocalDateTime. The rule does not model visit duration, travel time, preparation time, or partial overlaps.
  • Doc has one schedule and does not model multiple doctors, doctor availability, time zones, or recurring visits.
  • All current and previous datetimes are unique across patients, including past datetimes. These records do not verify attendance or completion. Previous dates do not count toward per-day current-appointment capacity.
  • A data file created by an older version may contain duplicate visit dates. The migration and data-preservation risks are described under the current implementation limitations above.

Optional date of birth

Person retains an optional DateOfBirth alongside blood type, emergency contact, and visit history. Add and edit accept dob/; omitted values preserve existing data, while an empty value clears it during edit. Storage defaults missing or null dateOfBirth fields to an unrecorded value for older files. Patient cards and details show the recorded date and completed age below the name, before blood type.

Optional blood type

Person stores a BloodType enum containing the eight blood types and UNKNOWN for unrecorded values. The existing constructor defaults to UNKNOWN. ParserUtil#parseBloodType trims whitespace, ignores letter case, and rejects empty or invalid input. Add and edit recognize bt/ and reject repeated prefixes; edit maps an explicitly empty value to UNKNOWN. Other edits and visit rescheduling preserve blood type.

JsonAdaptedPerson stores the display value (e.g. A+) in the bloodType property. Missing or null properties from older files load as UNKNOWN; an empty string represents a cleared value. Invalid stored values are rejected. Both patient cards and the details panel show recorded blood type below the date of birth (or the name when DOB is absent), hiding and unmanaging the row when it is unrecorded. Patient identity continues to use name and phone number.

Optional allergies

Person stores immutable free-text Allergies. Surrounding whitespace is removed; empty text represents unrecorded information and is distinct from an explicit No known allergies entry. Multiple allergies can be written in one value, such as Penicillin; latex; the field does not interpret, split, or infer clinical information. ParserUtil#parseAllergies rejects blank add values, while edit maps blank all/ to an empty value. Both parsers reject repeated prefixes. Unrelated edits, next, and prev preserve the field along with other patient details.

JsonAdaptedPerson stores the allergies string and treats missing or null fields in older files as unrecorded. The right-hand details panel displays recorded allergies after blood type, before alcohol history and smoking status. Long values wrap within the scrollable panel. Unrecorded values hide the row without implying no allergies. Add/edit help follows the same field order; patient list cards and patient identity remain unchanged.

Optional alcohol history

Person stores an immutable AlcoholHistory alongside blood type. It holds free text with surrounding whitespace removed; empty text represents unrecorded history and remains distinct from the explicit text Does not drink. ParserUtil#parseAlcoholHistory rejects blank add values, while edit maps an explicitly blank alc/ to an empty history. Both parsers reject repeated alc/ prefixes. Unrelated edits, next, and prev preserve the history.

JsonAdaptedPerson saves the alcoholHistory string and treats missing or null fields in older files as unrecorded. The right-hand details panel displays recorded alcohol history immediately after allergies, wraps long text, and hides the row when unrecorded. Patient list cards and duplicate-patient identity remain unchanged.

Optional smoking status

Person stores a SmokingStatus enum with NEVER, FORMER, CURRENT, UNKNOWN, and UNRECORDED. UNKNOWN represents explicitly recorded uncertainty; only UNRECORDED hides the row in the details panel. SmokingStatus#fromString trims surrounding whitespace and normalizes letter case using Locale.ROOT. ParserUtil#parseSmokingStatus rejects blank or unsupported recorded values, while edit maps blank smk/ to UNRECORDED. Both parsers reject repeated smk/ prefixes. Other edits, next, and prev preserve smoking status.

JsonAdaptedPerson stores the normalized lowercase status, or an empty string for unrecorded values. Missing or null smokingStatus fields in older files load as UNRECORDED; unsupported saved values are rejected. The right-hand details panel displays smoking status immediately after alcohol history. Patient list cards and patient identity remain unchanged. Add/edit help places [smk/STATUS] after [alc/ALCOHOL_HISTORY].

Editing patient details

EditCommandParser accepts optional replacement fields, including vd/ and note/. The displayed format is edit INDEX [n/NAME] [p/PHONE] [a/ADDRESS] [vd/DATETIME] [e/EMAIL] [ec/[NAME, ]PHONE_NUMBER] [dob/DATE] [bt/BLOOD_TYPE] [all/ALLERGIES] [alc/ALCOHOL_HISTORY] [smk/STATUS] [note/NOTES] [t/TAG].... It checks index syntax and duplicate single-valued prefixes before parsing field values, then rejects a descriptor with no supplied fields. When vd/ is supplied, ParserUtil#parseVisitDate reuses the existing strict VisitDate validation for d/M/yyyy HHmm; valid past dates are accepted, while an empty vd/ is rejected.

EditPersonDescriptor stores the supplied visit date and time and note along with the optional replacement fields. EditCommand copies the descriptor, resolves the patient using the displayed list, and replaces the immutable Person. Omitted fields, including the visit date/time and notes, are preserved. An explicitly empty email, note, emergency contact, or tag field clears its existing value and counts as a supplied field.

Before replacement, EditCommand requires the current datetime to remain strictly later than the latest previous datetime. A valid past datetime is still allowed, and history is preserved unchanged. It permits an unchanged current date but rejects a value already used by another patient's current or previous dates, including hidden patients. The conflict check is repeated after confirmation so a slot taken while the prompt was pending cannot be introduced into the model. Chronology failures produce a command error explaining that the current datetime must be later than the latest previous visit and showing that previous datetime. This check occurs before constructing the replacement patient; the Person constructor independently enforces the record invariants for all callers.

The descriptor's nullable Note distinguishes omission from an explicitly empty Note(""). When note/ is present, the parser constructs the existing immutable Note from the tokenizer's value; otherwise, the descriptor's note remains null. Notes-only replacement and clearing both succeed without vd/. The descriptor copy preserves this distinction, and createEditedPerson uses the supplied note or preserves the patient's existing note. Supplying the same note again, or clearing an already-empty note, succeeds.

The existing tokenizer uses String#strip() on outer whitespace, preserves internal spaces, and recognizes prefixes at the start of the arguments or after Java whitespace. A recognized prefix inside notes delimits another field; there is no quoting or escaping for literal prefix text, or extra note validation. Repeated note/ prefixes are rejected before field validation, including identical or empty values. Repeated t/TAG prefixes retain their existing replacement and clearing behavior.

Editing replaces the supplied fields without appending visit-history entries or per-visit notes. Saving and UI behavior follow the shared visit-change flow below.

Saving and displaying visit changes

edit, next, and confirmed prev validate the proposed change before replacing the patient. A valid prev first returns a non-saving CommandInputRequest; only its confirmed callback replaces the captured patient. Successful commands preserve the active filter and sort comparator, allowing the replacement patient to move or disappear as those rules are reevaluated, and return feedback with a CommandResult that requests saving. LogicManager saves through storage before returning the result to the UI.

These results select the replacement patient for the details panel, refreshing the record and calendar label even if the patient moves or disappears from the displayed list. view can still select any displayed patient without requesting a save.

Validation errors and cancelled confirmations leave patient data, saved data, and list context unchanged. Duplicate-related errors and name-confirmation prompts can display an existing patient in the details panel; other rejected inputs do not change that panel. If storage reports an I/O or permission failure, LogicManager restores the patient data, active filter, and sort captured before command execution. The command reports the save error, while the data file and displayed model remain consistent with the last successful save.

Sorting displayed visits by date

sort date [START_DATE] orders the patients in the currently displayed list without changing the active filter. SortCommandParser accepts an optional cutoff date in d/M/yyyy format. When it is present, the parser supplies the date to SortCommand; otherwise, the command obtains today's date from its clock when it executes. The command then creates a comparator that separates visits before the cutoff date from those on or after it.

The activity diagram shows how the cutoff date is selected and the comparison decisions made while the displayed list is being sorted. The underlying SortedList decides how many comparisons are required.

When exactly one visit is before the cutoff date, the comparator places the other visit first. Otherwise, it places the earlier visit date and time first. For example, with 21 October as the cutoff, visits on 22 October, 24 October, and 20 October are displayed in that order.

SortCommand passes the comparator to Model#sortFilteredPersonList. ModelManager applies it to the SortedList layered over the current FilteredList, so the displayed patients are reordered without replacing the stored patient list. A later operation that resets the filter also clears this display-only ordering.

Displaying visits as an agenda

agenda START_DATE [DAYS] shows current visits in a consecutive range of calendar days. AgendaCommandParser requires a start date and accepts an optional duration from 1 to 365 days. A bare agenda command displays the usage message, while an omitted duration defaults to seven days. The constructor checks that the final included day is on or before 31 December 2099, the last day a visit date can have (VisitDate.MAX_YEAR), so a range never extends past dates that can hold visits. The parser reports an invalid range before execution when this bound is exceeded.

AgendaCommand constructs a VisitDateWithinRangePredicate using an inclusive start and exclusive end. The exclusive end keeps the predicate independent of visit times: a seven-day agenda starting on 27 October accepts every time from 27 October through 2 November and rejects every time on 3 November. The command replaces the current filter with this predicate and applies a chronological comparator to the existing SortedList.

Filtering and sorting remain display-only. The address book retains its stored order, and the command returns a non-saving result. A later list restores the full list in stored order.

Finding patients by field

find filters the displayed patient list by name, phone number, address, tag, visit date, and notes. Each field has its own prefix, and every keyword must follow one: n/, p/, a/, t/, vd/, or note/. Keywords given for one field match a patient if any of them matches, while different fields must all match. For example, find n/m t/morning lists patients with a name word starting with m who also have a tag starting with morning.

Search criteria as predicates

Each field is searched by its own Predicate<Person> class in the Model component, and MatchesAllCriteriaPredicate combines them. FindCommand stores this single combined predicate, so it does not need to know which fields were searched.

  • FieldContainsKeywordsPredicate holds a field's keywords and implements test as "any keyword matches". It also implements equals, hashCode, and toString, comparing exact classes so that, for example, a name predicate and an address predicate with the same keywords are not equal. Each subclass only defines how one keyword matches its field:
    • NameContainsKeywordsPredicate, AddressContainsKeywordsPredicate, and NoteContainsKeywordsPredicate match the start of any word, ignoring case, using StringUtil#containsWordStartingWithIgnoreCase.
    • PhoneContainsKeywordsPredicate matches any part of the number, so remembered final digits are enough.
    • TagContainsKeywordsPredicate matches the start of any tag, ignoring case.
  • VisitDateOnDaysPredicate does not extend the keyword base class because it stores parsed LocalDate values. It matches a patient whose current visit falls on any given calendar day, at any time. Previous visit dates are history, so they are not searched.
  • MatchesAllCriteriaPredicate returns true only when every criterion matches, which gives the AND behavior across fields.

Parsing and execution

The sequence diagram below shows find n/m t/morning. The filtering loop is conceptual: the model's FilteredList evaluates the predicate for each stored patient whenever the displayed list is recomputed.

FindCommandParser#parse handles the arguments in these steps:

  1. It tokenizes the arguments. ArgumentTokenizer recognizes prefixes at the start of the arguments or after Java whitespace, so spaces, tabs, and line breaks separate fields consistently. A prefix-looking token separated by whitespace still starts a new field because the tokenizer has no quoting or escaping mechanism.
  2. It rejects text before the first prefix with MESSAGE_KEYWORDS_NEED_PREFIX and repeated prefixes with the shared duplicate-prefix error.
  3. For each prefix that is present, it splits the value into keywords and creates that field's predicate. An empty prefix such as n/ is rejected. Phone keywords must be digits. Visit dates are parsed strictly with VisitDate#DAY_INPUT_FORMATTER (d/M/yyyy), so impossible dates and dates followed by a time are rejected and the error names the invalid value.
  4. If no prefix was given, it shows the usage message; otherwise it wraps the predicates in a MatchesAllCriteriaPredicate and returns a FindCommand.

FindCommand#execute calls Model#updateFilteredPersonList, which also clears any sort ordering, and reports the number of matches. When nothing matches, the message lists every search prefix rather than a name-only hint, so the advice also suits phone, address, tag, visit date, and note searches.

Design considerations

Aspect: how plain keywords such as find alex are handled

  • Alternative 1 (current choice): Require a prefix for every keyword and reject plain keywords with an error that shows how to search by name and by phone number.
    • Pros: Every keyword visibly belongs to one field, so a search never mixes fields by accident.
    • Cons: Users of the earlier name-only find must add n/.
  • Alternative 2: Treat keywords before the first prefix as name keywords.
    • Pros: find alex keeps working.
    • Cons: Two ways to search names, and mistakes such as a missing prefix silently become name searches.

Aspect: how fields are represented

  • Alternative 1 (current choice): One predicate class per field, combined by MatchesAllCriteriaPredicate.
    • Pros: Adding a field, as vd/ and note/ did, needs a new small class and one parser line, without changing FindCommand or the existing predicates. Each predicate is tested on its own.
    • Cons: More classes than a single predicate holding every field's keywords.
  • Alternative 2: One predicate that stores a keyword list for each field and checks them all.
    • Pros: Fewer classes.
    • Cons: Every new field changes the same class, and its test method grows with a branch per field.

Scheduling the next visit

NextCommand appends the current datetime to the previous-date list and sets the requested datetime as current, preserving all other patient fields. This separates advancement from edit, which corrects the current datetime without adding history. The User Guide provides syntax and errors.

Eligibility requires current <= now and current < requested. The requested visit may be in the past, which supports entering follow-up visits retrospectively without inventing a temporary future appointment. Combined with the existing record chronology, this preserves history < old current < requested. An unchanged datetime keeps its specific error; an earlier datetime reports that it must be later than the current recorded visit.

The parser passes an injected clock to the command. Each eligibility check reads it once in the local time zone. Comparisons retain seconds and nanoseconds. An appointment at or before now requires confirmation; a future appointment does not require the time warning. Fixed clocks make boundary tests deterministic.

Before replacement, the command rejects an unchanged datetime and checks the complete candidate record against all other stored patients, including hidden patients and excluding the original record. The shared visit-date uniqueness rule applies.

If the requested visit is at or before now, or moves to a different day with Model.MAX_VISITS_PER_DAY (7) or more current visits, the command combines all applicable warnings in one CommandInputRequest before mutating. A later visit on the same day skips only the capacity warning, because it replaces that day's visit. On confirmation, the command rechecks eligibility using a fresh clock reading, verifies that the original record is unchanged, and repeats the conflict check before replacing the patient. If a future appointment reaches or passes now while a capacity prompt is open, it returns a new prompt including the time warning; only a subsequent y applies that operation. Prompts and cancellation do not mutate, save, or refresh the details panel.

Restoring the previous visit

PrevCommand discards the current datetime and replaces it with the latest previous datetime, removing the restored datetime from the previous-date list. There is no redo. It copies all other fields from the selected patient's latest record, preserving intervening edits. The User Guide includes syntax, feedback, and a running example.

There is no clock eligibility check: rollback must allow immediate correction of mistaken advancement, even while the current or restored datetime is still in the future. Every valid rollback first returns a CommandInputRequest containing the selected patient's current name and phone, the restored and discarded datetimes, and the confirmation instruction. The initial execution does not mutate, reset, refresh, or save anything.

The shared follow-up input handling trims the response and compares it to y case-insensitively; other responses are consumed as cancellation. The shared visit-change persistence flow describes when the confirmed mutation is saved. For this feature, the request captures the immutable selected Person and invokes a private rollback helper only after confirmation. The helper checks the stored person list with full Person.equals semantics before creating the replacement. If an intervening edit or deletion changed the record, it throws the stale-selection error without changing the replacement record or displayed list. Otherwise it calls createUpdatedPerson and replaces the captured patient while retaining the active filter and sort comparator.

Empty previous dates produce a CommandException before the private rollback helper runs. The helper's assertion documents that internal precondition, while user-input validation remains effective with assertions disabled. The replacement contains only dates from the original record, so it cannot introduce a new cross-patient datetime conflict. The model still enforces chronology and uniqueness on replacement.

Follow-up command-line input and confirmation

CommandInputRequest lets any command collect an additional command-line input through the existing command box and result display. It contains the prompt and a response handler. The handler receives the raw next input and the Model, then returns a CommandResult. That result can complete the interaction or contain another CommandInputRequest, so future commands can implement multi-step input without adding command-specific state to the UI or parser.

LogicManager stores at most one pending request. While a request is pending, LogicManager#execute(String) sends the submitted text to the request handler instead of AddressBookParser. This includes blank input and text that would otherwise be a valid command. After the handler returns or throws a CommandException, the old request is no longer pending. A handler can continue the interaction by returning a result containing a new request.

CommandResult separates displaying feedback from saving patient data. Prompts, cancellations, and the already-empty clear result do not cause a file write. A confirmed mutation returns a result that causes LogicManager to save the updated patient data once.

The shared CommandInputRequest#createConfirmation helper trims the response and compares it to y without regard to case. It runs the supplied action only for that response; every other response returns the supplied cancellation message.

For additions with a name duplicate or a full visit day, and for same-name edits, AddCommand and EditCommand use the same confirmation helper as destructive commands. The prompt does not mutate or save patient data. Confirmation performs the captured mutation and saves once; every other response cancels without saving. The proposed patient is captured before the prompt, and confirmed actions recheck both the true-duplicate and unique-visit-date invariants before modifying the model.

For delete INDEX, DeleteCommand validates the index and captures the exact displayed Person before requesting confirmation. The prompt contains only that person's name because other fields can be absent. Confirmation deletes that captured object rather than resolving the index again. If the record changed or disappeared while confirmation was pending, the command reports that the selected person no longer exists and deletes nothing.

For clear, ClearCommand requests confirmation only when Doc contains patient records. Its prompt uses entry for one record and entries otherwise. Confirming clears the patient list; every other response cancels.

Command history navigation

CommandHistory stores each non-empty ordinary submission as an exact string unless it is identical to the newest history entry. This collapses consecutive exact duplicates while retaining identical submissions separated by another command. CommandBox records the text before calling its command executor, so commands that later fail parsing or execution remain available. Before recording, CommandBox checks whether Logic has a pending CommandInputRequest; follow-up responses are excluded from command history because they are input for an existing command rather than new commands.

The history position starts immediately after the newest entry. On the first Up arrow press, CommandHistory saves the current command box text as a draft and returns the newest command. Further Up presses move towards older commands and stop at the oldest entry. Down presses move towards newer commands; moving past the newest entry restores the saved draft. A new ordinary submission resets the position to immediately after the newest entry.

CommandBox handles JavaFX key-pressed events for the Up and Down arrow keys, replaces the text, positions the caret after the recalled text, and consumes the event so the key does not also move the caret. Other keys retain the usual TextField behavior. The history belongs only to the current CommandBox, so it is discarded when the application closes.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current patient-record state in its history.
  • VersionedAddressBook#undo() -- Restores the previous patient-record state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone patient-record state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial patient-record state, and the currentStatePointer pointing to that single state.

Step 2. The user executes delete 5 to delete the 5th patient in Doc. The delete command calls Model#commitAddressBook(), causing the modified patient-record state to be saved in addressBookStateList, and the currentStatePointer is shifted to the newly inserted state.

Step 3. The user executes add n/David …​ to add a new patient. The add command also calls Model#commitAddressBook(), causing another modified patient-record state to be saved into addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the patient-record state will not be saved into addressBookStateList.

Step 4. The user decides that adding the patient was a mistake and executes undo. The command calls Model#undoAddressBook(), shifts currentStatePointer once to the left, and restores the previous patient-record state.

Note: If currentStatePointer is at index 0, pointing to the initial patient-record state, there are no previous states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should work without requiring an installer, and without the user having to install any software other than Java.
  3. Should support local patient management, visit planning, and the offline command directory without an internet connection. Opening the hosted full User Guide from Help requires internet access.
  4. Should support at least 1,000 patient records, with up to 100 previous visit datetimes and one patient-level note per record.
  5. Target: Should respond to each valid command within 2 seconds when operating on 1,000 patient records with up to 100 previous visit datetimes and one patient-level note per record. This excludes the time spent entering the command. Verification: Not yet verified; a benchmark under this workload remains to be run.
  6. For common tasks such as adding, finding, listing, editing, scheduling, and restoring patient visits, a user who types at above-average speed should be able to complete the task faster through the CLI than by using the mouse.
  7. A doctor who has not used a CLI application before should be able to add a patient and look up that patient's record within 15 minutes of reading the User Guide.
  8. Should save every change to the local data file before accepting the next command, so that at most one command's worth of data is lost if the app terminates unexpectedly.
  9. Should store all patient data only on the user's own machine, so that no patient data leaves the doctor's computer.
  10. Should start up and be ready to accept a command within 5 seconds on a typical modern laptop.
  11. Should not crash or lose existing records if the data file has been manually edited into an invalid state; it should instead report the problem and start with an empty caseload.
  12. Should be delivered as a single JAR file of no more than 100MB, so that it can be copied onto a laptop taken on house visits.

NFR 6 is an unverified usability goal. The team must agree on a concrete mouse-versus-CLI comparison procedure before it can be assessed.

Glossary

  • Active patient record: A patient record included in the doctor's current caseload and visit planning.
  • Archived patient record: A patient record retained for future reference but excluded from the active caseload and visit planning.
  • Calendar label: Past, Today, or Upcoming beside the current datetime, based on its calendar date relative to the local date when details are rendered. It does not indicate attendance or completion.
  • Caseload: The collection of active patient records currently managed by a doctor.
  • Current visit date: The required date and time stored in visitDate. It can be past, present, or future and remains stored until changed using edit, next, or prev. It must differ from every other current or previous datetime.
  • House call: A medical consultation carried out at the patient's home rather than at a clinic.
  • House-call doctor: A doctor who travels to patients' homes to provide medical consultations and follow-up care.
  • Medical condition: An ongoing health issue recorded in a patient's notes to help the doctor prepare for future visits.
  • MSS: Main Success Scenario; the sequence of steps in a use case when nothing goes wrong.
  • Next visit date: The current visit datetime used for planning. The field remains required after its time passes.
  • Overdue visit: A planning term for a current visit datetime that has passed. Doc does not determine whether the visit took place.
  • Patient record: The information Doc stores for one patient, including their contact details, medical notes, tags, current visit date and time, and previous visit dates and times retained by next.
  • Priority level: A label indicating how closely a patient needs to be followed up, used when ordering planned visits.
  • Rollback: Restoring the latest previous visit datetime with prev, replacing and discarding the current datetime while preserving the patient's other details. It is not a general undo operation and has no redo.
  • Visit: A single house call. Doc stores one current datetime, ordered previous datetimes, and one patient-level note.
  • Visit record: A patient's current and previous visit datetimes. These record scheduled times retained by the user and do not verify attendance or completion.

Optional alcohol history

Person stores an immutable AlcoholHistory alongside blood type. It holds free text with surrounding whitespace removed; empty text represents unrecorded history and remains distinct from the explicit text Does not drink. ParserUtil#parseAlcoholHistory rejects blank add values, while edit maps an explicitly blank alc/ to an empty history. Both parsers reject repeated alc/ prefixes. Unrelated edits, next, and prev preserve the history.

JsonAdaptedPerson saves the alcoholHistory string and treats missing or null fields in older files as unrecorded. The right-hand details panel displays recorded alcohol history immediately after allergies, wraps long text, and hides the row when unrecorded. Patient list cards and duplicate-patient identity remain unchanged.

Optional smoking status

Person stores a SmokingStatus enum with NEVER, FORMER, CURRENT, UNKNOWN, and UNRECORDED. UNKNOWN represents explicitly recorded uncertainty; only UNRECORDED hides the row in the details panel. SmokingStatus#fromString trims surrounding whitespace and normalizes letter case using Locale.ROOT. ParserUtil#parseSmokingStatus rejects blank or unsupported recorded values, while edit maps blank smk/ to UNRECORDED. Both parsers reject repeated smk/ prefixes. Other edits, next, and prev preserve smoking status.

JsonAdaptedPerson stores the normalized lowercase status, or an empty string for unrecorded values. Missing or null smokingStatus fields in older files load as UNRECORDED; unsupported saved values are rejected. The right-hand details panel displays smoking status immediately after alcohol history. Patient list cards and patient identity remain unchanged. Add/edit help places [smk/STATUS] after [alc/ALCOHOL_HISTORY].
